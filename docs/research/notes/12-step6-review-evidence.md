## The warnings thread

The row in [Daemon and CLI](../../decisions.md#daemon-and-cli) that starts "The daemon writes its warnings to stderr from one thread":

With stderr a pipe that was full, a daemon whose `ranking.json` did not parse had not bound its socket after 10 s, because the start waited to write the warning. With the thread, the same daemon bound after 1.02 s and answered `status` (reproduced on 2026-10-17). Once the clip ids had run out and stderr was full, each copied answer that warned got no reply within 5 s, nor did `status`, because the owner loop waited to write the warning. With the thread, 13 copies and `status` replied at once, and once stderr drained it got 9 warnings and `lyncast: 3 warnings were dropped while stderr was full`, and with 11 copies 9 warnings and `lyncast: 1 warning was dropped while stderr was full` (each reproduced on 2026-10-17). While Quit's wait for its replies ended with the second its warnings took, a Quit with stderr full lost its reply in 9 of 10 runs with the daemon on one CPU, and with a second for each wait it lost none of 20. While the last line was a write of its own after the wait, a second daemon whose stderr was full was still running 10 s later, and through the thread it exited 1 after 1.02 s (each reproduced on 2026-10-17). While the line of a daemon whose warnings thread did not start was a write that waited for stderr, a daemon that could start no thread, under an `RLIMIT_NPROC` of 0, with stderr full was still running 10 s later, waiting in `pipe_write`, and with the line written only when stderr has room it exited 1 after 0.005 s (each measured on 2026-10-17). That check came before the write, so a daemon stopped between the two while another writer filled stderr waited in `pipe_write` until stderr drained (round 5 review, reproduced on 2026-10-17). Stopped at its write while another writer filled stderr, a daemon whose write the timer cuts off exited 1 after 1.001 s in 3 of 3 runs, where one that wrote only when stderr had room was still in `pipe_write` after 20 s (each measured on 2026-10-17). Started with `SIGALRM` blocked, a mask that a process inherits across exec, a daemon whose write the timer cuts off, under an `RLIMIT_NPROC` of 0 with stderr full, was still in `pipe_write` after 6 s with the signal pending (round 6 review, reproduced on 2026-10-18), and once the write unblocked the signal it exited 1 after 1.02 to 1.07 s in 3 of 3 runs (measured on 2026-10-18).

## The capture thread's reads

The row in [Clipboard and paste](../../decisions.md#clipboard-and-paste) that starts "The capture thread reads one representation per offer":

TinyCast reads a file URL before text ([notes/06](06-tinycast-behaviour-spec.md)). A list with only an `https://` link would otherwise drop the copy. While a list that was not UTF-8 dropped the offer, a seed of such a list beside `hello` as text added no row (reproduced on 2026-10-17). The `Watcher` hands back the offers it has queued without looking at its cancel pipe (`src/watch.rs:308-315`), so with four stopped seeders and a Quit 2.5 s after the first, the daemon exited 3.51 s after the Quit, and 1.50 s after it once the thread checked for the cancel before each offer (each reproduced on 2026-10-17). While the preview decoded each path it reached to its end, a list of one path of 25 MiB decoded 26,214,393 bytes for a preview of 1,024 (round 6 review, reproduced on 2026-10-18), which took 199 ms at the median of 7 runs in a release build, and in a debug build a copy made right after that list was offered failed with `not copied: the clipboard watcher did not confirm the selection` at 2.5 s in 5 of 5 runs, at a load average of 22 to 25. ## The load of the clips

The row in [Clipboard and paste](../../decisions.md#clipboard-and-paste) that starts "The writer thread opens `clips.sqlite3` and loads it":

sqlite3 3.40 waited on a FIFO at the database's path until `timeout` stopped it after 5 s (reproduced on 2026-10-17). SQLite opens a database and its journal by path, not through a descriptor the daemon checked, so a FIFO swapped in after the check, or one at `clips.sqlite3-journal`, holds the open for good. With a FIFO at the journal's path, the daemon had not bound its socket when `timeout` stopped it after 9 s (reproduced on 2026-10-17). The bounded wait turns that race into a start with the rows in memory. A stored preview of 32 MiB loaded whole and took the daemon's `Pss_Anon` from 776 to 33,568 kB, and with the bound the same file left the rows in memory at 732 kB (each reproduced on 2026-10-17). A stored type of 32 MiB did the same, from 744 to 33,560 kB, and `clip list --json` printed 33,554,510 bytes, and with the bound the file left the rows in memory at 724 kB (each measured on 2026-10-17). A Wayland message gives its size in 16 bits (the protocol's wire format), so no type that a capture reads holds 65,535 bytes, and the daemon's own rows always load. In a table without `STRICT`, a row whose last use held 32 MiB of text failed the load only once the daemon's peak RSS had reached 42,068 kB, against 10,140 kB with a number there, and a count of used ids of 32 MiB of text at 107,840 kB, because SQLite hands over the whole value before rusqlite finds that it is not an integer. With the types checked first, the same files left the rows in memory at a peak of 10,480 and 10,176 kB. The count's row is found by its name, which the load measures before it compares it: a name of 32 MiB in a row of `sqlite_sequence` ahead of it took the peak to 42,440 kB while it was compared, and to 10,496 kB once measured first (each measured on 2026-10-17). While the load created the table before it checked the file, a database with another program's table and a count of used ids that was text gained a `clips` table before it was refused, and a load whose open took 7 s made an empty file 12 KiB long after the start had gone on with the rows in memory (codex review, reproduced on 2026-10-18). Under `locking_mode=EXCLUSIVE`, a `BEGIN EXCLUSIVE` that was rolled back kept the lock, so a second connection's read and its own `BEGIN EXCLUSIVE` got `database is locked`, and it left an empty file and a file with a table byte for byte as they were. On the empty file it wrote a journal of 512 bytes, which stayed until the connection closed, and with the journal in memory it wrote none. `CREATE TABLE IF NOT EXISTS` left a file that held the table byte for byte as it was (SQLite 3.53.2, each measured on 2026-10-18). A file in WAL mode stayed as it was only while its `-wal` held no frames. With frames there, the connection checkpointed them into the file as it closed after the load, and removed the `-wal`: another program's file went from 4,096 to 8,192 bytes once the load had refused it, and a lyncast file from 4,096 to 12,288 bytes after the start had gone on without its load (verification of the fix, reproduced on 2026-10-18). With the checkpoint on close turned off, the file and its `-wal` stayed byte for byte as they were in both cases. A writer killed in a transaction left another program's file at 98,304 bytes beside a journal of 9,728, and the load that refused it rolled the file back to the 8,192 bytes that it held before that transaction and removed the journal (each measured on 2026-10-18). Beside an empty file, the load removed a `-wal` of 12,392 bytes, a journal, and a FIFO at the journal's path, and the file stayed empty (SQLite 3.53.2, measured on 2026-10-18). While the load did not check the table's columns, a `clips` table without a `preview` column failed it with SQLite's own error, `no such column: preview`, followed by the whole select of the load's checks over many lines (verification, reproduced on 2026-10-18). While the load compared the hash with `GLOB '*[^0-9a-f]*'`, which stops at a NUL byte, a hash of 63 hex digits and a NUL passed it, and the load failed with rusqlite's `Invalid column type Text at index: 4, name: hash` (verification, reproduced on 2026-10-18). With `ltrim`, which reads every byte, the same file gave `clip 1: a hash that is not lowercase hex` (measured on 2026-10-18).
